Projection notes

How R2 reads Claude Code

The local server tails the session transcript in ~/.claude/projects and extracts only the shape of each event: which tool was called, whether the result was an error, which subagent it came from. The session content never leaves your disk and is never sent to the page.

Module mapping

  • SNS video sensor → Read, Grep, Glob, LS
  • SCP scomp link arm → Bash and shell
  • MAN fine manipulator → Write, Edit, MultiEdit
  • TRX transceiver → WebSearch, WebFetch, MCP tools
  • VCK VicksVisc projector → Task and subagent lines
  • EXT fire extinguisher → tool_result with is_error
  • INT Intellex IV → model prose and token count
  • LOC locomotion → human turns and session activity

None of that is arbitrary: every module is a documented piece of R2-series equipment, assigned to the kind of work it resembles.

The fleet

Each live subagent gets its own droid, and the series comes from the model behind the event. Canon: the R4 is identical to the R2 except its dome is conical rather than hemispherical, and the R5 has a shorter cone head and was the cut-price, unreliable unit. So opus runs as an R2, sonnet as an R4, haiku as an R5. The size difference encodes the model tier — that part is a reading aid, not a canonical dimension.

Nesting is inferred, not read

The transcript gives each subagent an agentId and an attributionAgent, but the latter is the agent type (general-purpose, fork) — there is no parent id anywhere in the format. So when a subagent calls Task and a new agent file appears shortly after, this page attaches the new droid to that one as a child and tethers it there. It is a heuristic based on timing, and it is labelled as such rather than presented as fact.

Colour channels

  • green — logic-display blip, a clean tool_result
  • red — logic-display blip, a failed one
  • amber — whole-body alarm, the extinguisher firing
